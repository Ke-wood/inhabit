# 桌宠与直播

> 两个新场景，两套节奏，两条技术路线。
> 核心原则：**同一套心智，不同的外壳。**

---

## 1. 为什么要分场景

她已经能在 QQ/微信里聊天了。加桌宠和直播，不是为了「多两个入口」，
而是因为**这两个场景对节奏的要求完全相反**：

| | QQ / 微信 | 桌宠 | 直播 |
|---|---|---|---|
| 对方在等吗 | 会等，但能忍 | 不看屏幕，感知不到 | **观众等不了** |
| 合适的思考间隔 | 20 秒 | 60–180 秒 | 0.5–3 秒 |
| 上下文预算 | 完整 | 中等 | **极简**（只接眼前） |
| 输入 | 消息 | 屏幕变化 | 弹幕 |

如果把这三套统一成一套参数，必然有一方是错的：
- 按 QQ 的 20 秒 → 直播里她像个木头
- 按直播的 0.5 秒 → 群里她变成复读机

**所以参数必须跟着场景走，而不是跟着程序走。**

---

## 2. 两套外壳

技术路线不一样，因为窗口需求根本不同：

```
        ┌──────────────────────────────────────┐
        │            core/ （心智，共用）        │
        │  记忆 / 人格 / 关系 / 念头 / 行动       │
        └────────────┬─────────────┬───────────┘
                     │             │
        ┌────────────▼───┐   ┌─────▼──────────────┐
        │  desk: 桌宠     │   │  live: 直播         │
        │  PySide6 透明窗口│   │  VTube Studio       │
        │  三视图 PNG 精灵 │   │  Live2D 参数 + 口型  │
        └────────────────┘   └────────────────────┘
```

| | 桌宠 | 直播 |
|---|---|---|
| 渲染 | 我们自己画（PySide6） | VTS 画（我们只发参数） |
| 形象 | 三视图 PNG 精灵 | Live2D 模型 |
| 窗口 | 透明、无边框、置顶、可拖 | VTS 自己的窗口，被 OBS 采集 |
| 为什么不能用同一个 | Live2D 做不到「透明置顶可拖」 | PySide6 做不到「口型表情」 |

**这个分工不是妥协，是各自的最优解。**

## 3. 桌宠

### 3.1 它长什么样

借用了开源项目 `1190fasheqi/dafeiyu-pet`（MIT）的窗口层：

- 无边框、透明背景、始终置顶
- 三视图行走（正面/侧面/背面，侧向自动镜像）
- 拖拽、鼠标穿透、托盘、右键菜单
- 气泡说话，支持「心声」模式（灰色斜体括注）

### 3.2 它和心智怎么通

**不共享进程**。桌宠是独立进程，通过本机 socket 通信：

```
core/pet_link.py  (主程序侧，纯标准库)
        │  JSON 行协议，127.0.0.1:8791
        ▼
tools/pet_window.py  (桌宠侧，需要 PySide6)
```

原因：PySide6 有 80MB + 会拉起 Qt 事件循环，塞进主程序会污染「纯标准库」的卖点，
也会让没装 Qt 的用户连主程序都跑不起来。

指令只有三种：

```jsonc
{"cmd": "say",   "text": "饿了", "inner": false}
{"cmd": "mood",  "energy": 0.42, "mood": "有点累"}
{"cmd": "state", "state": "thinking"}     // idle/walking/thinking/talking/sleeping
```

**桌宠没开时，主程序不受影响**（`PetLink` 静默失败）。

### 3.3 怎么装

```bash
pip install -r requirements-pet.txt      # 只装 PySide6
python tools/fetch_pet_sprites.py        # 下载素材（不进仓库）
python tools/pet_window.py               # 开桌宠
```

主程序这边：`config.json` 的 `scenes.desk` 里打开，或面板勾选。

## 4. 直播

### 4.1 为什么要 VTube Studio

不是因为它最好，是因为**它是唯一不用我们自己渲染的**：

- 不碰渲染引擎 → 不用集成 Cubism SDK
- 不分发模型 → 不踩美术版权
- 许可干净 → Live2D 官方那条「把 SDK 编进 AI 产品需审核」的条款约束的是 VTS 开发者，不是我们

**一旦我们自己渲染，就落进那个条款。** 这是不自己画的最重要理由。

### 4.2 我们发什么

VTS 的 WebSocket API（`ws://localhost:8001`）：

| 消息 | 用途 |
|---|---|
| `AuthenticationTokenRequest` / `AuthenticationRequest` | 首次授权，拿 token 后可复用 |
| `InjectParameterDataRequest` | 写口型、角度、眼睛、身体参数 |
| `HotkeyTriggerRequest` | 触发表情/动作/换模型 |
| `Live2DParameterListRequest` | **启动时探测真实参数名** |

**参数名必须探测，不能写死**：VTS 侧叫 `MouthOpen`，模型侧叫 `ParamMouthOpenY`，
写死必挂。这是 wallie-V2 踩过的坑。

### 4.3 口型怎么做

**第一版：音量包络**（纯标准库，单核 0.87%）

逐帧算 RMS → 平滑 → 映射到 `MouthOpen`。只分「张/合」，不分元音。

为什么这就够：人眼对「嘴有没有动」远比「动得对不对」敏感，包络能拿到约 70% 的可信度。

**第二版：时长驱动 viseme**

edge-tts 能给逐字时间戳（`boundary="WordBoundary"`），加上 `pypinyin`
把字转成韵母，就能按时间轴查表出口型。

**为什么不用 wallie 的频谱法**：实测普通话 6 个元音只对 5 个，`ü` 被判成宽唇
（它真实的 F2 在 1900Hz，掉进了它的「高频段」）。这不是调参能救的。

### 4.4 一个必须注意的坑：口型要跟**播放**，不是跟**合成**

wallie 在这里有缺陷：它在合成完就推口型，而播放是异步排队的，
**口型最多领先声音 8 秒**。

正确做法二选一：
1. 不自播，把音频交给虚拟声卡，让 VTS 自己监听做口型（同步成本为零）
2. 自己播，但把「已播到哪」回传给口型模块

## 5. 场景参数

三个画像，全部可从 `config.json` 覆盖：

| 参数 | chat | desk | live |
|---|---|---|---|
| `min_think_gap` | 20 | 60 | 0.5 |
| `idle_think_gap` | 60 | 180 | 3 |
| `poll_sec` | 2.0 | 2.0 | 0.2 |
| `recall_limit` | 12 | 8 | **3** |
| `facts_here` | 8 | 6 | **2** |
| `max_steps` | 3 | 1 | 1 |
| `speak_gap` | 0 | 0 | 0 |

**`recall_limit` 和 `facts_here` 是直播的关键**：
直播时她不需要想起三天前的事，只需要接住眼前这句。
这两个值一压，prompt 反而比 QQ 更小——**上下文爆炸的问题是这么解的，不是靠少存**。

### 覆盖方式

```jsonc
"scenes": {
  "desk": { "min_think_gap": 90 },
  "live": { "min_think_gap": 1.0, "recall_limit": 4 }
}
```

只写要改的字段，其余用默认画像。

### 硬约束

**chat 画像必须与现有默认值完全一致。** 这不是配置问题，是回归保护：
QQ/微信现在的 20 秒间隔是调出来的，绝不能因为加了直播被顺手改掉。

## 6. 流式输出

你说得对，这一块不得不做。

### 6.1 现状的问题

`core/brain.py` 现在是：
```python
with opener.open(req, timeout=60) as resp:
    data = json.loads(resp.read())     # 一次读完
```

必须等整段生成完，才拿到文本，才去合成语音。

用户感受：「模型动一下说句话，卡顿几秒」。

### 6.2 要做的两层

```
LLM 流式 ──► SentenceStreamer ──► TTS 逐句合成 ──► 播放
   ↑                ↑
 首字节 1.1s    遇句末标点就切
```

- **`speak_stream()`**：SSE 增量返回，但要处理 thinking 块跨 chunk、空 delta、断流
- **`SentenceStreamer`**：把 token 流切成「能拿去合成的句子」
  - `。！？；…` 和换行 → 切
  - `，、` → **不切**（切了语音会很碎）
  - 兜底：40 字找逗号切，60 字强制切

### 6.3 别忘了 `speak()` 不能变

现有 6 个调用方（mind/act/reflect/sleep/diary/browse）都依赖 `speak()` 的同步返回。
流式是新方法，不是替换。

## 7. 三件事的优先级

| 优先级 | 事 | 为什么这个顺序 |
|---|---|---|
| 1 | 场景参数 | 不改任何技术栈，能立刻验证「按场景切节奏」这个核心假设 |
| 2 | 流式 | 直击用户体感「卡顿」 |
| 3 | 桌宠窗口 | 需要 PySide6，是可选增强 |
| 4 | VTS 直播 | 依赖最多，最后做 |

先做 1 和 2，是因为它们**对现有代码是加法**；3 和 4 是新增技术栈。

---

## 8. 已知的坑

- **`channel_for()` 是子串匹配**（`p in s`），`live:` 场景名里不能含 `qq_` 之类的子串，否则会被误判渠道
- **素材版权**：桌宠的 PNG 是社区二创，MIT 只覆盖代码不覆盖美术。所以不进仓库，用户自己下载
- **Live2D 许可**：我们自己不渲染就没问题；一旦集成 Cubism SDK 就落入「需审核」条款
- **PySide6 体积**：80MB+，必须做成可选依赖，不能进主 `requirements.txt`
- **口型对齐**：跟播放进度，不跟合成进度
